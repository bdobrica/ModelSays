# PB-00 Gameplay Baseline

Measured 2026-07-19 on a local WSL development environment with PostgreSQL 16 in Docker, Go 1.25, Node.js 22, curated English content, and no external provider calls. The harness called the real HTTP handler and PostgreSQL repository in isolated schemas; it did not open network sockets or sleep for the three-second polling interval.

## Workload

Each 3-, 8-, or 12-player workload creates a room, joins all identities, starts one round, polls once per identity, submits one curated answer per identity, immediately polls until that committed submission is visible, reveals, and polls once per identity again. Database counts exclude schema creation and migrations. `poll requests/minute` projects the current client policy of one room GET per active player every three seconds.

Run:

```bash
make baseline
```

The command builds the production client and prints versioned JSON. It requires the configured PostgreSQL database but creates and removes only isolated `modelsays_baseline_*` schemas.

The built client was 3 files and 256,715 bytes uncompressed in both passes (Vite reported 78.83 KiB gzip for JavaScript and 2.10 KiB gzip for CSS). Request, poll, query, and bundle counts matched exactly. Response bytes varied by at most 0.39% because serialized timestamps have variable fractional precision. Backend p95 varied by at most 13.0%; mutation-visible averages varied by at most 14.8%. These results meet the documented repeatability tolerances.

Mutation-visible time is an immediate refetch measurement, not the current user's polling wait. With three-second polling, the added user-visible delay is normally 0–3 seconds. Query counts describe the workload rather than one request; later changes should compare like-for-like workloads and inspect query growth per additional player.

## Initial beta targets

These are engineering budgets, not evidence that unbuilt features already meet them:

- HTTP p95 ≤ 200 ms and unexpected HTTP error rate < 1% for a representative 12-player room.
- Pushed committed mutation p95 ≤ 500 ms; reconnect/refetch p95 ≤ 3 seconds.
- Durable deadline transition p95 lag ≤ 1 second.
- Provider p95 ≤ 10 seconds, at most one retry, and estimated provider cost ≤ US$0.10 per five-round game.
- Production client assets ≤ 350 KiB uncompressed and ≤ 110 KiB compressed.
- Baseline deterministic counts must match; response bytes must stay within 1%; investigate timing regressions above 25% in the same environment.

The targets for pushed updates, automatic transitions, providers, and error rate are intentionally `Not measured` until their owning plan steps add the behavior and measurement.

## Limitations

- This is a local serial workload, not a concurrency, saturation, internet, browser-rendering, or multi-instance test.
- PostgreSQL query duration includes local driver round trips but not query plans or server resource sampling.
- Response size is JSON body size and excludes HTTP/TLS framing.
- The harness measures immediate state visibility; it projects polling volume rather than waiting in real time.
- Human comprehension, fun, host workload, mobile usability, and mode demand require structured playtests using `docs/playtest-guide.md`.
